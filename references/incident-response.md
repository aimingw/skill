# 事故响应流程 + 复盘模板

生产事故的处理流程和复盘规范。
目标：快速恢复业务 + 找到根因 + 防止再犯。

## 事故响应流程

### 第0阶段：发现（0-1分钟）

发现途径：
- 监控告警（Prometheus/Zabbix/Grafana）
- 用户反馈（客服转达）
- 主动巡检发现

**发现后第一件事：确认是不是真的出事了。**
- 告警可能是误报（监控探针挂了/网络抖动）
- 用户反馈可能是个例（用户自己网络问题）
- 用 30 秒确认：curl 测试 / 看监控大盘 / 问业务方

### 第1阶段：止血（1-15分钟）

**核心原则：先恢复业务，再查根因。**

止血手段按优先级排序：

| 优先级 | 手段 | 适用场景 | 风险 |
|--------|------|---------|------|
| 1 | 回滚 | 发版导致的问题 | 低（有回滚预案时） |
| 2 | 重启服务 | 进程异常/内存泄漏 | 低（临时措施） |
| 3 | 切流量到备机 | 单机故障 | 低（有备机时） |
| 4 | 降级/限流 | 流量过大/依赖故障 | 中（影响部分功能） |
| 5 | 扩容 | 容量不足 | 中（需要时间） |
| 6 | 重启服务器 | 系统级故障/资源耗尽 | 高（丢内存中的数据） |

**止血决策树：**

```
确认故障
├── 是刚发版吗?
│   ├── 是 -> 立刻回滚
│   └── 否 -> 继续
├── 是单机还是集群?
│   ├── 单机故障 -> 摘流量/切备机
│   └── 集群故障 -> 继续
├── 能重启解决吗?
│   ├── 能（临时）-> 重启 + 继续查根因
│   └── 不能 -> 继续
├── 是资源耗尽吗?
│   ├── 磁盘满 -> 紧急清理
│   ├── 内存满 -> 限制进程/加swap
│   ├── 连接数满 -> 重启/调限制
│   └── CPU满 -> 限流/扩容
├── 是依赖故障吗?
│   ├── 数据库 -> 切从库/降级读
│   ├── 缓存 -> 本地缓存/降级
│   └── 下游服务 -> 熔断/降级
└── 都不是 -> 深入排查根因
```

### 第2阶段：通报（5分钟内）

**通报内容（简明）：**
```
【事故通报】
时间：2024-01-01 10:00
级别：P1
现象：XXX服务502，影响YYY功能
当前状态：正在排查/已止血/已恢复
负责人：XXX
下一步：XXX
```

**通报渠道：**
- 内部群（运维/开发/业务）
- 上级领导（P0/P1）
- 用户公告（如果影响用户）

### 第3阶段：根因定位（止血后）

止血后开始查根因，按5步法执行：
1. 现象收集
2. 影响评估
3. 分层排查
4. 根因定位
5. 修复+验证

**注意：** 不要在生产环境做实验性排查。如果需要复现，在测试环境复现。

### 第4阶段：修复（确认根因后）

- 修复根因（不只是症状）
- 验证修复有效
- 确认没有引入新问题
- 观察至少30分钟

### 第5阶段：恢复

- 全量恢复流量/服务
- 确认所有告警消除
- 确认业务正常
- 通知相关人员

## 事故分级标准

| 级别 | 标准 | 响应时间 | 到场时间 | 通报范围 |
|------|------|---------|---------|---------|
| P0 | 核心业务全挂/数据丢失/安全事件 | 立即 | 5分钟 | 全公司 |
| P1 | 部分功能不可用/性能严重劣化 | 5分钟 | 15分钟 | 运维+开发+业务 |
| P2 | 非核心功能异常/告警但未影响用户 | 30分钟 | 1小时 | 运维内部 |
| P3 | 容量预警/潜在风险 | 2小时 | 计划窗口 | 工单记录 |

## 复盘模板

事故恢复后48小时内完成复盘。

```markdown
# 事故复盘：[简短标题]

## 基本信息

| 项目 | 内容 |
|------|------|
| 事故时间 | 2024-01-01 10:00 ~ 10:30（30分钟） |
| 影响范围 | 首页打不开，影响全部用户 |
| 事故级别 | P0 |
| 发现方式 | 监控告警 |
| 恢复方式 | 回滚发布 |
| 值班人员 | XXX |

## 时间线

| 时间 | 事件 |
|------|------|
| 09:55 | 发布新版本v2.3.1 |
| 10:00 | 监控告警：首页502率飙升 |
| 10:01 | 值班人员收到告警，确认故障 |
| 10:02 | 判断为发版引起，决定回滚 |
| 10:05 | 开始回滚 |
| 10:08 | 回滚完成，首页恢复 |
| 10:10 | 确认全部恢复，通报 |
| 10:30 | 开始根因分析 |

## 影响评估

- 用户影响：首页不可访问30分钟，约XXX用户受影响
- 业务影响：订单损失约XXX元
- 数据影响：无数据丢失/损坏

## 根因分析

### 直接原因
新版本代码中数据库连接池配置错误，maxActive写成了1，
导致只有一个数据库连接可用，高并发时连接耗尽。

### 深层原因
1. 代码Review时没有检查数据库连接池配置变更
2. 预发布环境没有做压测（只做了功能测试）
3. 发布流程缺少灰度/分批发布机制
4. 监控告警没有覆盖连接池指标

### 为什么在10:00才触发
- 09:55发布后5分钟内流量较低，1个连接还能撑住
- 10:00流量高峰到来，连接立即耗尽

## 修复措施

### 临时止血
- 回滚到v2.3.0

### 根因修复
- 修正连接池配置
- 在配置中心增加参数范围校验

## 预防措施

| 措施 | 负责人 | 截止时间 | 状态 |
|------|--------|---------|------|
| 预发布环境增加压测环节 | XXX | 2024-01-10 | 待办 |
| 发布流程改为灰度发布 | XXX | 2024-01-15 | 待办 |
| 增加连接池指标监控告警 | XXX | 2024-01-07 | 待办 |
| 代码Review增加配置变更检查项 | XXX | 2024-01-05 | 待办 |

## 经验教训

1. 发版不是结束，是开始。发布后15分钟内要密切关注监控。
2. 回滚预案必须提前准备，不是出了事才想怎么回滚。
3. 功能测试不能替代压测，很多问题只在压力下暴露。
4. 配置变更和代码变更一样危险，必须纳入Review流程。

## 附录

- 事故期间监控截图
- 相关日志片段
- 回滚操作记录
```

## 安全事件特殊处理

如果怀疑是安全事件（被入侵/被攻击/数据泄露），处理方式完全不同：

```
常规事故：先恢复再查因
安全事件：先保全现场再处理

常规事故：重启服务止血
安全事件：不要重启（可能丢失证据）

常规事故：修改配置修复
安全事件：先隔离机器，用副本分析
```

### 安全事件应急步骤

```bash
# 1. 隔离（不关机，保留内存数据）
# 断网但不断电
ip link set eth0 down    # 临时断网
# 或在交换机/安全组层面隔离

# 2. 保全证据
# 内存dump
dd if=/dev/mem of=/tmp/mem.dump bs=1M   # 可能不完整
# 进程列表
ps auxf > /tmp/ps.log
# 网络连接
ss -tnap > /tmp/ss.log
# 登录记录
last -50 > /tmp/last.log
lastb -50 > /tmp/lastb.log
# 计划任务
crontab -l > /tmp/cron.log
cat /etc/crontab > /tmp/crontab.log
ls -la /var/spool/cron/ >> /tmp/crontab.log
# 异常文件
find /tmp /var/tmp /dev/shm -type f -exec ls -la {} \; > /tmp/suspicious_files.log
# 最近修改的文件
find / -mtime -1 -type f 2>/dev/null > /tmp/recent_files.log
# 日志
journalctl --since "24 hours ago" > /tmp/journal.log
# 进程的命令行和环境
ls -la /proc/*/exe 2>/dev/null > /tmp/proc_exe.log
cat /proc/*/cmdline 2>/dev/null | tr '\0' ' ' > /tmp/cmdline.log

# 3. 分析
# 看异常进程
ps aux | grep -v "^\(root\|daemon\)" | grep -E "python|bash|nc|curl|wget"
# 看异常网络连接
ss -tnp | grep -E "ESTAB|LISTEN" | grep -v "127.0.0.1"
# 看异常定时任务
grep -r . /etc/cron* /var/spool/cron/ 2>/dev/null
# 看 authorized_keys
cat /root/.ssh/authorized_keys 2>/dev/null
cat /home/*/.ssh/authorized_keys 2>/dev/null

# 4. 清理和恢复
# 这一步应该在分析完成后才做
# 最好重装系统而不是"清理"
```

## 常见误操作和预防

| 误操作 | 后果 | 预防 |
|--------|------|------|
| `rm -rf /` 或 `rm -rf $VAR/` (VAR为空) | 删全盘 | 变量为空保护: `rm -rf "${VAR:?}/path"` |
| `chmod -R 777 /` | 全盘权限混乱 | 永远不要对/递归改权限 |
| `kill -9 1` | 杀init进程 | 不要kill PID 1 |
| `dd if=/dev/zero of=/dev/sda` | 清空磁盘 | 确认of目标 |
| 在生产机执行测试脚本 | 不可预知 | 测试和生产隔离 |
| 发版后不看监控 | 故障扩大 | 发布后盯盘15分钟 |
| 用root做日常操作 | 误操作风险 | 日常用普通用户+sudo |
| 不备份直接改配置 | 不可回滚 | 改前先备份 |
